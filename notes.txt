1. PROBLEM AND GOAL
-----------------------------------------------------------------------------
A robot must find a target object in a building. It only has a structured
description of the building derived from an IFC model (rooms, their function,
the equipment inside, doors/connectivity). A VLM/LLM reasons about WHERE the
object is likely to be, a route over the likely rooms is planned, and at each
stop a camera image is checked by a vision model.

Pipeline (current):
  0. Task interpretation  - classify input: find_object / go_to_room /
                            building_query / none (local LLM via Ollama)
  1. Semantic ranking     - LLM gives raw 0-1 score per room -> softmax -> p(room)
  2. Route planning       - take rooms until prob_mass covered, order the visit
                            (Held-Karp optimal for small N, greedy NN fallback)
  3. Visual confirmation  - image at each stop sent to a vision model

3. DESIGN DECISIONS: WHAT WAS CHOSEN AND WHY NOT THE ALTERNATIVES
-----------------------------------------------------------------------------

3.1 Own IFC cleaning script (clean_ifc.py) vs. generic IFC->JSON converter
    Candidate rejected: buildingSMART ifcJSON converter
    (https://github.com/buildingsmart-community/ifcJSON), added to the repo as
    file_converters/ in commit 072ebd3 (2026-09-30).
    Findings [FACT, user's tests]:
      - With IfcOpenShell 0.8.5 the converter crashed on import.
      - After patching it, it shortened every GUID. On the IDAC model all 15
        rooms collapsed onto 2 IDs, so it is impossible to tell which furniture
        belongs to which room -> breaks the room->equipment mapping that the
        whole pipeline depends on.
      - Repo's last listed update: April 2024 (stale w.r.t. current
        IfcOpenShell).
    Defence of own script:
      - Uses the current IfcOpenShell API directly.
      - Keeps only what the task needs: spatial hierarchy, every IfcSpace
        (name/function/area/centroid), equipment (IfcFurniture /
        IfcBuildingElementProxy) with its containing room, doors with the rooms
        they connect. Output is small enough to fit in the LLM context.
      - A generic converter is lossless but huge (geometry, property sets) and
        not room-centric; the LLM would need further filtering anyway.
    Status: converter kept in file_converters/ as a reference/baseline, not part
    of the active pipeline.

3.1b clean_ifc.py v2: generic extractor instead of a keep-list (2026-10-09)
    What: keep-list (IfcSpace/IfcFurniture/IfcBuildingElementProxy/IfcDoor)
    replaced by "every rooted entity except a blacklist" (IfcAnnotation,
    IfcGrid, IfcStructuralItem/Activity/AnalysisModel). Output split into
    <name>_full.json (everything) and <name>_llm.json (rooms, equipment,
    adjacency). Records keyed by GlobalId; names are display only.
    Why:
      - A keep-list silently loses anything the exporter modelled with another
        class (IfcFlowTerminal sinks/lights, IfcFurnishingElement in IFC2X3).
        A blacklist fails open and is schema-agnostic (tested IFC2X3/4/4X3).
      - Name-keyed v1 output cannot handle duplicate or numeric room names
        (Revit: Name "101", LongName "Office"). Same failure class as the
        ifcJSON GUID collapse in 3.1.
      - Units: v1 assumed metres. v2 converts every length/area/volume/angle
        (direct attributes via the schema's declared measure type, psets/qtos
        via their measure type or own Unit). Verified: synthetic_office
        converted to mm gives identical output.
      - Door connectivity: v1 used only IfcRelSpaceBoundary, which many
        exports lack (ac20 has 0 boundaries). v2 adds a geometric fallback
        (probe 0.5 m either side of the door along its local Y axis,
        point-in-polygon against space footprints) and records the source.
      - Equipment-to-room: relation first (containment, spatial reference,
        aggregation parent chain), then centroid point-in-polygon; recorded
        as room_source = relation | geometric.
      - Pset dropping: substring keywords ("material", "energy", ...) replaced
        by exact names (DROP_PSET_EXACT, initially empty, extend with
        --drop-pset). Substrings can hit useful psets; the audit lists every
        pset name seen, so the drop list is chosen from evidence.
      - Silent `except: pass` removed: every caught exception is counted by
        stage | class | error type in the audit (semantic-quality variable).
      - Geometry: one multi-threaded ifcopenshell.geom.iterator pass instead
        of create_shape per entity; footprint = union of projected triangles
        (shapely), centroid = footprint centroid (v1 used the vertex mean,
        biased for L-shaped rooms).
    Alternatives considered:
      - Keep v1 and add classes to the keep-list: does not generalise to
        unseen exporters.
      - Export resource entities as records (like ifcJSON): huge and not
        object-centric; resources are folded into the object that uses them.
      - Separate script for the LLM view: kept in one file behind
        --no-llm-view so both views come from the same run.
    Deviations from the written plan (decided while implementing):
      - ObjectPlacement, RepresentationMaps, HasPropertySets also dropped from
        the attribute dump (represented by geometry / psets instead).
      - IfcSlab excluded from obstacles (it is the floor); only slab openings
        are added, as floor-level hazards.
      - When IfcRelSpaceBoundary links a door to >2 spaces (Duplex_A), the
        geometric probe picks the two spaces actually either side of it.
      - Models without IfcBuildingStorey (IDAC_Model: spaces directly under
        IfcSite) get one whole-model obstacle/grid layer; audit.no_storeys.

3.3 Softmax over LLM scores instead of using raw scores / a fixed threshold
    Raw scores are not a probability distribution and do not respect "rooms
    already ruled out". Softmax gives p_i = exp(s_i/T)/sum_j exp(s_j/T) that
    sums to 1; ruled-out rooms are removed BEFORE the softmax so their mass is
    redistributed. Alternative (fixed score threshold, earlier --threshold
    flag) does not scale with building size; it is kept only as an alias of
    --min_prob. [RATIONALE: README/code]

3.4 Cover prob_mass (0.9) instead of fixed top-k
    Scales with the building: a sharp distribution -> 1-2 rooms, a flat one ->
    many. Fixed k would over-visit when the model is confident and under-visit
    when it is not. min_prob 0.01 drops negligible rooms.

3.5 Route ordering: Held-Karp (optimal) for few rooms, greedy nearest-neighbour
    otherwise. Held-Karp is exact but O(n^2 2^n), so greedy is the fallback for
    larger buildings. Start room falls back to the first room in the JSON when
    not given / not found (real models do not have a room called "Reception").

3.6 Task-interpretation stage (stage 0) added before ranking (commit 7fe44dc)
    Without it every input (greetings, questions, "go to X") would be scored as
    a search task. It classifies intent, uses the last few exchanges as
    context (so "go there" resolves), restricts to a named room, and
    short-circuits to rooms where the building model already records the
    target (e.g. a printer model number = printer). Ambiguous room references
    are refused with the room list rather than guessed.
    test_interpreter.py was added to batch-check phrasings without walking.

    Added build_ollama_options / add_ollama_args; flag renamed

3.9 Building questions: LLM plans, Python computes, LLM phrases (2026-10-14)
    <name>_llm.json only holds room function, equipment per room and
    adjacency, so it cannot answer sizes, colours, materials or properties.
    <name>_full.json has them but is ~3.3 MB for IDAC (~1M tokens vs.
    num_ctx 16384; Ollama truncates silently), and one record is ~2-3 KB of
    mostly irrelevant psets.
    Chosen: building_query.py. Step 1 the LLM sees a ~4.6k-char catalogue
    (rooms, element types with counts and colours, materials, field names)
    and returns a structured query (action, target, filters, field). Step 2
    Python applies the filters to EVERY record and computes counts / sums /
    averages / min / max exactly. Step 3 the LLM phrases the answer from the
    computed result only.
    Rejected: (a) whole full JSON in the prompt - does not fit. (b) LLM picks
    GUIDs, code fetches those records, LLM answers - the LLM would have to
    enumerate every match (misses are silent), many records still overflow
    the context, and counting / adding over dozens of records is unreliable
    for an LLM. (c) Enriching _llm.json with per-item details - only covers
    the fields chosen in advance and still leaves arithmetic to the LLM.
    Colour: RGB is mapped to a name by fixed HLS rules (colour_name), so the
    filter and the answer agree; colours are per surface style, so a chair is
    "black" and "bluish grey". Material names from Revit are often <Unnamed>
    or library paths; they are shortened, and missing ones are reported as
    not recorded. Windows/walls/columns have no containment relation; they
    are tied to rooms through IfcRelSpaceBoundary.
    Ranking and the interpreter keep using the _llm view (adapter
    from_llm_view in rank_candidates.py) - no change to the ranking prompt.

8.1 What an HTN (Hierarchical Task Network) is
    A classical planner (STRIPS/PDDL) searches for ANY action sequence that
    reaches a goal. An HTN planner instead starts from a high-level task and
    decomposes it with designer-written recipes until only executable actions
    remain. Components:
      - State: facts about the world (rooms, doors, rooms already searched,
        current belief about where the object is).
      - Primitive tasks / operators: executable actions with preconditions and
        effects, e.g. move_to(room), capture_view(), detect(object).
      - Compound tasks: abstract goals, e.g. find(object), search_room(r).
      - Methods: alternative decompositions of a compound task, each with its
        own preconditions. The planner takes the first method whose
        preconditions hold and backtracks if the decomposition fails.
    Properties: domain knowledge lives in the methods, so the search space is
    much smaller than in classical planning, and the decomposition tree
    explains why each action was chosen.
    References:
      - Erol, Hendler, Nau (1994): formal semantics of HTN planning.
      - Nau et al. (2003), JAIR: SHOP2.
      - GTPyhop (Dana Nau): small Python HTN planner, fits the current stack.
      - Hoeller et al. (2020): HDDL, PDDL-style language of the hierarchical
        track of the International Planning Competition; usable as formal

8.2 Mapping onto the current pipeline
    find(object)
    |- m_direct     [IFC contains the object as a modelled element]
    |    move_to(element.space) -> detect(object) -> confirm
    |- m_semantic   [object not modelled; infer from room function]
         rank_rooms(object)        <- LLM room scorer (priors)
         order_route(ranked_rooms) <- Held-Karp
         for r in route: search_room(r)
           |- m_found:     move_to(r) -> capture_view -> detect -> stop/continue
           |- m_not_found: mark_searched(r) -> update_beliefs -> replan
    Roles of existing components:
      - <name>_llm.json / _full.json from clean_ifc.py = initial state.
      - LLM room scores = method ordering and room priority.
      - Held-Karp = helper inside m_semantic.
      - VLM detection = primitive operator whose effect updates the state.
      - "update plan" in the loop = re-decomposition of the remaining task tree
        after a failed detection.
    Single- vs multi-target (open item) = two methods for find():
      - one stops at the first confirmed detection ("find a cup");
      - one continues until all candidate rooms above a probability threshold
        are searched ("find all fire extinguishers").
      The LLM's parse of the instruction chooses between them.

8.3 How an HTN differs from the current implementation
    [FACT] SearchSession (interactive_search.py) runs one fixed recipe in
    plain Python: interpret -> (rooms recorded in IFC, or rank all rooms with
    the LLM) -> softmax -> Held-Karp -> visit, detect, stop on success.
    Variations are if/else branches inside run_task. It is effectively a
    single-method HTN already, so moving to an HTN is a refactor, not a rewrite.
    For the current test cases the robot would likely do the same actions in
    the same order. What changes:
      1. Choosing strategies: several methods for find(object) (modelled in
         IFC / room scoring / find-all); the planner picks by state instead of
         branches buried in the loop.
      2. Plan validity: operators have preconditions, e.g. move_to(room)
         requires the room to be reachable through a door in the IFC data.
         Invalid plans are rejected; today the room list is trusted as built.
      3. Inspectable plan: the decomposition tree (which method, which steps
         from which task) can be logged, shown as a thesis figure, and
         compared against an LLM-only plan. Today the plan is only an
         implicit room list.
      4. Replanning from state: after a failed detection the remaining plan is
         rebuilt from the updated state instead of moving down a fixed list.
         Almost identical with one strategy; matters once a failure can
         switch method.
    The HTN does NOT make the search faster or more accurate by itself; room
    scoring and Held-Karp do that. It adds structure, extensibility and an
    evaluable formal planning component.

8.4 Where the LLM sits (three options)
    a) LLM generates the whole plan. Easy, no guarantees (non-existent rooms,
       violated preconditions). Use only as the evaluation BASELINE.
    b) LLM grounds and parameterises; symbolic HTN decomposes.  <- CHOSEN
       LLM turns the instruction into a goal task, object class and
       constraints; the scorer supplies priors; GTPyhop (or own planner)
       guarantees every plan is valid against the IFC state.
       Measurable contribution: plan-validity rate and steps-to-find,
       LLM-only vs LLM+HTN.
    c) LLM writes new methods at runtime. A research topic of its own; out of
       scope for a master's thesis.

8.5 Alternatives to HTN (for the related-work / design-justification section)
    Option                    Examples                      Verdict
    ------------------------  ----------------------------  -------------------
    Classical planning (PDDL) LLM+P (Liu et al., 2023):     Considered, rejected
      + LLM translator        LLM -> PDDL goal, planner     (see below)
                              (e.g. Fast Downward) solves
    POMDP / belief-space      Wandzel et al. (2019) multi-  Theoretical upper
      planning                object search; GenMOS (Zheng  bound, out of scope
                              & Tellex, 2023)
    LLM-only planning         SayCan (Ahn et al., 2022);    Baseline
                              ProgPrompt (Singh et al.,
                              2023); Code as Policies
                              (Liang et al., 2022)
    LLM over a scene graph    SayPlan (Rana et al., 2023)   Closest related work;
                                                            must cite and contrast
    Behaviour trees / state   -                             Execution control,
      machines                                              not a planner
    Details:
      - PDDL: plans guaranteed valid, standard language reviewers like. But the
        whole domain must be modelled carefully, and classical planners assume
        a fully known world; an unknown object location is exactly what they
        handle badly. Object search is a fixed recipe, not a puzzle needing
        open search, so HTN fits better.
      - POMDP: robot keeps a probability distribution over object locations and
        picks actions that best reduce uncertainty, modelling imperfect
        detection. Most principled; directly models room priors and detector
        misses. Hard to implement, slow beyond small problems, and would turn
        the thesis into a POMDP thesis. Use in the literature review as the
        theoretical ideal.
      - LLM-only: flexible and fast to build; no validity guarantee and
        run-to-run variance (already observed with the local models).
        SayCan additionally weights LLM suggestions by skill feasibility.
      - SayPlan: LLM searches a 3D scene graph of a building (collapsing /
        expanding floors and rooms) and checks its plan in a simulator before
        execution. IFC data is effectively a scene graph. Difference to argue:
        this thesis uses IFC semantics and explicit probabilities instead of an
        LLM browsing the graph.
    Thesis structure suggested: HTN as the choice; PDDL as the considered and
    rejected alternative (modelling effort, poor fit with unknown object
    locations); POMDP as the principled upper bound, out of scope; LLM-only
    and SayPlan-style planning as related work and baselines. Covers task 1
    (literature) and the design justification in one section.

8.6 Belief update after a failed detection (links task 3 and task 4)
    [FACT] Current code: rooms already searched are passed as `exclude` and
    REMOVED before the softmax (rank_and_plan), i.e. P(r) := 0.
    Proposed: a negative detection does not prove absence. With detector
    detection rate d (miss rate 1 - d):
        P'(r)  = P(r) * (1 - d)          for the searched room r
        P'(r') = P(r')                   for every other room r'
        then renormalise so that sum P' = 1.
    Keeps the probabilistic part (task 3) and the planning part (task 4)
    connected instead of describing two separate mechanisms.

8.7 Caveats

      technical rooms and kitchens first and not stopping at a single
